# 1. Objective

مقایسه و تصمیم‌گیری درباره‌ی نحوه‌ی توزیع سرویس‌ها روی سرورها (توپولوژی)، و استاندارد سیستم‌عامل برای همه‌ی سرورهای اکوسیستم.

---

# 2. گزینه‌های توپولوژی

## گزینه الف — استاندارد، دو سرور ثابت

```
Server 1: Frontend + HAProxy
Server 2: API (FastAPI) + Odoo + PostgreSQL
```

| سرور | سرویس‌ها | Baseline پیشنهادی (DOC-051) |
|---|---|---|
| Server 1 — Frontend | HAProxy + Next.js | 2 vCPU / 2 GB RAM / 20 GB SSD |
| Server 2 — Business | FastAPI + Odoo + PostgreSQL + Redis | 8 vCPU / 16 GB RAM / 200 GB NVMe SSD |

**مزیت:** ساده، هزینه پیش‌بینی‌پذیر، مدیریت آسان با تیم کوچک.
**محدودیت:** جداسازی بیشتر (مثلاً PostgreSQL روی سرور مستقل) نیاز به Migration دستی بعدی دارد.

## گزینه ب — Cloud Node (مقیاس‌پذیر، پرداخت بر اساس مصرف)

سرویس‌ها روی Node های Cloud جداگانه (مثلاً Managed PostgreSQL، Container per Service) با امکان Scale مستقل هر بخش.

**مزیت:** مقیاس‌پذیری مستقل هر سرویس، بدون نیاز به تخمین دقیق از قبل.
**محدودیت:** پیچیدگی عملیاتی بیشتر، هزینه متغیر، نیاز به تخصص DevOps بیشتر.

# 3. تصمیم

**گزینه الف (استاندارد، دو سرور ثابت) برای فاز اول انتخاب می‌شود** — هم‌راستا با اصل کلی پروژه («سادگی و سرعت رسیدن به v1»، طبق تصمیمات قبلی این پروژه). Cloud Node به‌عنوان مسیر رشد آینده (وقتی نیاز واقعی مقیاس‌پذیری اثبات شد) باقی می‌ماند، نه انتخاب فاز اول.

## 3.1 نام‌گذاری نهایی سرورها (تأیید‌شده)

```
i-srv-1 (Business):  Odoo + PostgreSQL + API Gateway + Redis + Object Storage
i-srv-2 (Frontend):   Next.js + HAProxy
```

**تصمیم Redis و Object Storage:** هر دو روی `i-srv-1` قرار می‌گیرند (نه Frontend) — چون مستقیماً توسط Odoo/API مصرف می‌شوند (Session/Cache برای Odoo، فایل پیوست تیکت/گزارش برای Odoo/API)، و نزدیک‌بودن به این دو تأخیر (Latency) را کاهش می‌دهد؛ ارتباطی مستقیم و پرتکرار با Next.js ندارند.

# 4. استاندارد سیستم‌عامل

**تصمیم:** تمام سرورها — بدون استثنا — **Ubuntu 26.04 LTS Minimal** خواهند بود.

| دلیل | توضیح |
|---|---|
| یکپارچگی | همه سرورها (Frontend، Business، هر Node آینده) دقیقاً یک نسخه‌ی پایه دارند — کاهش خطای «فقط روی سرور من کار می‌کند» |
| سازگاری با محیط فعلی | محیط Staging فعلی همین پروژه (طبق DOC-040 §8) از قبل Ubuntu 26.04 LTS است — تجربه‌ی عملی این نسخه از قبل موجود است |
| Minimal | حداقل بسته‌های پیش‌فرض نصب‌شده = سطح حمله (Attack Surface) کمتر و منابع مصرفی پایه کمتر |
| پشتیبانی بلندمدت (LTS) | ثبات بیشتر برای محیط Production نسبت به نسخه‌های غیر-LTS |

# 5. موارد باز (نیاز به تصمیم بعدی)

## 5.1 پلن منابع برای مشتری جدید (Multi-Tenant Resource Plan)

سؤال مطرح‌شده: آیا برای هر مشتری/شرکت جدید (در صورت مدل چندمستأجری) یک پلن منابع جداگانه لازم است؟

**وضعیت:** هنوز تصمیم‌گیری نشده — نیاز به روشن‌شدن مدل تجاری دارد:
- آیا این اکوسیستم **تک‌مستأجر** (Single Company، فقط همین پروژه) است، یا **چندمستأجر** (SaaS برای چند شرکت مشتری) خواهد بود؟
- اگر چندمستأجر: آیا هر مشتری یک Database/Instance مجزای Odoo می‌گیرد، یا همه در یک Instance مشترک با جداسازی داده (Multi-Company) کار می‌کنند؟

> این تصمیم مستقیماً روی معماری DOC-051 (Sizing) اثر می‌گذارد — نیاز به یک نشست جداگانه‌ی تصمیم‌گیری دارد، پیش از قفل نهایی مدل منابع per-customer.
